## [Unreleased]

### Added
- **Windows itself from Microsoft's Security Update Guide (MSRC)**: a background sync reads Microsoft's CVRF API (`api.msrc.microsoft.com/cvrf/v3.0`, public) – the monthly documents of the last 24 months once, then every 6 hours the list of documents, downloading only new ones and revised ones (at most daily for the last two months, weekly for older ones; about 30 MB each), never during the vulnerability scan and not at startup. It stores per CVE and Windows release the security update (KB), the fixed build, severity, CVSS, and whether Microsoft reports the CVE as exploited or publicly disclosed, for the releases in an explicit mapping (Windows 10 1607/1809/21H2/22H2, Windows 11 23H2/24H2/25H2/26H1/26H2, Windows Server 2016/2019/2022/2025). A Windows node is affected when its build (e.g. `26100.9445`) is lower than the fixed build for its release; the fix is the release's newest cumulative update ("KB… closes N CVEs"), so superseded updates need no tracking. A revised document replaces its fixes, so fixes Microsoft changes or withdraws change or disappear with the next download. The findings join the existing ones (node page, counts, top lists, CVE lookup) with source `msrc`; exploited CVEs are marked and listed first. A Windows node without a build with update revision, of a release that is not mapped or without synced data is shown as *not checked* with the reason, never as unaffected. NVD stays the source for applications on Windows. `MSRC_SYNC=off` disables the download (`MSRC_HISTORY_MONTHS` sets the months kept); a document can be imported with `POST /api/v1/vulnerabilities/msrc/documents` (`settings:write`), and `GET /api/v1/vulnerabilities/msrc` shows the sync and how many Windows nodes were checked ([#192](https://github.com/BenediktSchackenberg/octofleet/issues/192)).
- **Windows agent: one log per component**, like the ConfigMgr client logs ([#330](https://github.com/BenediktSchackenberg/octofleet/issues/330), step 1): `Agent.log`, `Inventory.log`, `Jobs.log`, `Updates.log`, `Remediation.log`, `Security.log`, `Events.log`, `LiveData.log`, `RemoteTools.log` and `SelfUpdate.log` in `C:\Windows\Logs\Octofleet`, mapped from the logging class. `Agent.log` also gets every warning and error of all components. Lines are in the CMTrace format (CMTrace/OneTrace highlight warnings and errors and merge logs by time) with component, type and thread; `Text` is an option. Each file rotates at 2 MB and keeps 4 old files (`Updates-20261124-153000.log`), instead of one daily `service-*.log` with 10 MB and 14 files. New `Logging` section in `service-config.json`: format, default level, level per component (e.g. `"Levels": { "Updates": "Debug" }`), file size and old files, read at service start (default Information, as before). The inventory collectors, the inventory push (size, HTTP status, duration, the server's answer on a rejected push), the package manager and the Windows Update search and installation now log what failed: the empty `catch { }` blocks on these paths write a debug or warning line, so a section missing from the inventory can be traced on the node. Update searches and installations started by a job log to `Updates.log`. Signed URLs and install arguments are not logged. Written like before (one write per line, no extra thread or process); `update.log` of the self-update stays. Old `service-*.log` files are deleted when they are 14 days old.
- **CVE lookup** on the vulnerabilities page: a search field with suggestions while typing (`CVE-2026-987` or `2026-987`) answers "which nodes are affected by CVE-X?" – the CVE's severity, CVSS score, publication date, description and NVD link, and every affected node with its operating system, the affected packages and versions, the version that fixes each (or *no fix yet* / *fix unknown*), whether a kernel package is the running kernel, and a link to the CVE on the node page. It says explicitly whether no node is affected (with the time of the last scan) or the CVE is unknown to Octofleet; the looked-up CVE is kept in the URL (`?cve=`). API: `GET /api/v1/vulnerabilities/cves/{cve_id}` (404 for an unknown CVE) and `GET /api/v1/vulnerabilities/cves?q=` for suggestions (prefix, at least the year, at most 50), both with `vulnerabilities:read`. Only data of the existing scans is used ([#195](https://github.com/BenediktSchackenberg/octofleet/issues/195)).
- Windows nodes: the Security tab shows **App Control for Business (WDAC)** (enforcement in kernel and user mode – enforced / audit / off – the active policies and the vulnerable driver blocklist), **AppLocker** (per rule collection: enforced / audit / off with the rule count, and whether the Application Identity service runs) and **Virtualization-based security** (VBS, Credential Guard, memory integrity/HVCI, System Guard Secure Launch). The Windows agent reads them from `Win32_DeviceGuard`, `CiTool --list-policies` (closed input, 30 s limit; without CiTool the policy files in `CiPolicies\Active`), the CI registry key and `Get-AppLockerPolicy -Effective`; a check that cannot be read shows *unknown* and does not affect the rest of the inventory. The server stores them normalised (`appControl`, `appLocker`, `vbs` in `GET /api/v1/inventory/security/{node_id}`). Shown only, no security findings yet; needs the agent from this release ([#227](https://github.com/BenediktSchackenberg/octofleet/issues/227)).
- **Agent long-poll** ([#283](https://github.com/BenediktSchackenberg/octofleet/issues/283), step 1: server and Linux agent): `GET /api/v1/agent/wait/{node_id}` (agent key, `jobs:poll`) holds the request until there is work for the node – a pending job or approved remediation job, a queued terminal command or a terminal page just opened, a new screen or shell session – and answers `{"wake": [...]}`, otherwise `{"wake": []}` after about 55 s (`AGENT_WAIT_SECONDS`, minus up to 10 % jitter). The routes that create work wake the node's request in-process; a check of the database and the terminal queue when the request comes in catches everything else (scheduled jobs that became due, jobs from paths that do not wake), and a wake-up while the agent is between two requests is kept for 2 minutes. One backend process, as Octofleet runs today; held requests answer when the server stops, so a restart does not wait for them. The Linux agent keeps one long-poll open in the background and runs the job, terminal or screen poll within a second when the answer names it; its timers become a fallback every 10 minutes (`LONG_POLL_FALLBACK_INTERVAL`). An idle Linux node sends about 1.4 requests per minute instead of about 13 (25 with a screen capture tool), 10,000 idle nodes about 230 per second instead of about 2,200; a new job starts within about a second instead of up to a minute. After an error or a server restart the agent falls back to its timers and reconnects after a random 7–22 s (growing up to 5 minutes); against an older server (404) it keeps its timers and asks again hourly. Older agents keep polling as before. `LONG_POLL=false` turns it off. The Windows agent follows in a later step.
- **Windows agent MSI**: each release attaches `OctofleetAgent-v<version>.msi` (WiX v5, built in `release.yml` from the same checked files as the ZIP, SHA256 in `.msi.sha256.txt`). Silent install with `SERVER_URL`, `API_KEY` (hidden in `msiexec` logs), optional `DISPLAY_NAME`, `PUSH_INTERVAL` and `SCREEN_HELPER=1` (the screen helper is a feature, off by default); all properties are secure for managed installs. Listed in *Programs and Features*, version from the release tag, stable upgrade code: major upgrade, repair, uninstall and Windows Installer's return codes. The service `OctofleetNodeAgent` is installed, started, stopped and removed by the MSI, restarted on failure. The config in `C:\ProgramData\Octofleet` is not part of the package: upgrade, repair and uninstall keep it, passed properties replace only their own values, the folder is restricted to SYSTEM and Administrators and the service encrypts the key on its first start, as with the install script. The MSI installs over a script install (same folder and service, config kept, no re-enrolment). An agent installed by the MSI does not update itself (log line in the service log): deploy the new MSI. The `uninstall-agent` job and `Uninstall-OctofleetAgent.ps1` uninstall the MSI first. `installer/README.md` and `docs/AGENT-SETUP.md` have `msiexec` examples for Intune (LOB, Win32 with product code detection), ConfigMgr and GPO; the stale `0.5.1` version and `GATEWAY_*` properties are gone ([#332](https://github.com/BenediktSchackenberg/octofleet/issues/332)).
- **Patches → Linux approval rules** (`/patches/linux-rules`): the rules with their scope, updates and minimum age, enabled and disabled with a click; an editor with a live preview of what a rule covers (nodes, versions approved now, waiting, excluded, nodes without security data) and the server's validation; the deployment rings with pause and resume; the releases the agents report, marked when they have no security data (CentOS Stream, pacman); the totals over all Linux nodes and a note on the disabled example rule. **Fleet updates** installs Linux nodes too: the versions their rules approve, with the exact version; the list shows approved and waiting updates per Linux node, and the dialog says why a Linux node is skipped (agent too old for approval rules, pacman) with links to the node page or the rules ([#271](https://github.com/BenediktSchackenberg/octofleet/issues/271)).
- **Linux approval rules** (Patches API, `packages:write`): rules approve or exclude Linux package versions for all Linux nodes or the nodes of deployment rings (with the ring's delay) and groups, optionally per distribution release – security updates only (with a minimum severity on dnf/yum), package and repository patterns, a minimum age counted from when Octofleet first saw the version, *expedite* to skip the ring delay. An exclusion wins over an approval. Rings can be paused. A fresh installation has one disabled example rule and approves nothing. The fleet list counts approved and waiting updates per Linux node, and `POST /api/v1/patches/fleet/install` installs the approved versions on Linux nodes with their exact version – recomputed by the server when the job is created (the page for the rules and the Linux part of the install dialog follow). Distributions without security data (CentOS Stream, pacman) are marked. The counts come from a per-node cache that a background worker keeps current (fleet list: about 20 ms at 10,000 nodes x 150 updates and 20 rules) ([#271](https://github.com/BenediktSchackenberg/octofleet/issues/271)).
- **Reboot button** for Windows and Linux nodes: next to *Reboot required* on the node's Updates tab, in the node header and in *Patches → Fleet updates* (per row and for the ticked nodes). The dialog names the nodes and warns about logged-on users (both agents now report them with their live data), jobs that have not finished and open terminal, screen and shell sessions; it reboots now (in a minute), in N minutes or at a time (up to 7 days ahead) with an optional message to the users, and a scheduled reboot can be cancelled. New permission `nodes:reboot` (roles `operator` and `admin`), new job type `reboot` (`shutdown /r` on Windows, `shutdown -r` on Linux), audit entries `node.reboot` / `node.reboot_cancel`, API `POST /api/v1/nodes/reboot`, `POST /api/v1/nodes/reboot/preview`, `GET /api/v1/nodes/{node_id}/reboot`, fleet field `reboot_job`. *Reboot required* clears only when the node reports after the reboot. Needs agents from this release. On Linux systems without a D-Bus system bus, where `shutdown -r` cannot reach logind, the reboot runs from a systemd timer (`systemctl reboot`) and the job says that logged-on users are not warned.
- **Server: logging per component** ([#330](https://github.com/BenediktSchackenberg/octofleet/issues/330), step 1): every backend line names its component – `[Jobs]`, `[Inventory]`, `[Updates]`, … with the agents' names, plus `Api`, `Access`, `Auth`, `Alerts`, `Retention` and `Vulnerabilities` – so `docker compose logs backend | grep '\[Jobs\]'` shows one component. **Admin → Logging** sets a level per component (`components` in `GET`/`PUT /api/v1/settings/logging`, kept like the global level; default: all follow the global level). Requests rejected with 422 (wrong field types, broken JSON – before, only an access line) now get one warning with route, node, client, size and reason, never the body, at most one per node, route and reason in 10 minutes plus a count. The job endpoints log jobs handed out, started and their results (info; failed results as warnings) and every poll and agent wait at debug; remediation polls and results likewise. Unhandled errors are logged through the logger instead of printed. Still stdout only (Docker), no files per component.
- **Admin → Logging**: the backend's log level (error / warning / info / debug) and the access log (every request, only errors and slow requests, or off) can be changed without a restart (`GET`/`PUT /api/v1/settings/logging`, audited). Defaults are as before (info, every request). The request line now has the duration and no longer the query string (tokens in URLs stayed in the log); lines are written by a background thread. `LOG_LEVEL` sets the level until the setting is loaded. The `[LIVE-DATA] … network interfaces received` line (one per live-data push, about a quarter of all lines) is now debug. Measured cost of a line per request: about 4 % of the backend's maximum rate (docs/CONFIGURATION.md#logging).
- Docker log rotation for all services (`LOG_MAX_SIZE`, default 20m; `LOG_MAX_FILE`, default 5): the container logs had no limit.
- Linux nodes: each pending update shows whether it needs a reboot (*Needs a reboot* / *May need a reboot*), like Windows updates – before, only the install confirmation said so. The server estimates it per package (`reboot_behavior` in `GET /api/v1/inventory/linux/{node_id}`), and the node's list, the install confirmation and the fleet view all use that one estimate (the browser had its own copy of the rules). The fleet view's reboot badge names the updates behind it as tooltip (`reboot_updates` in `GET /api/v1/patches/fleet`, Windows too). Ubuntu's kernel metapackages (`linux-generic`, `linux-virtual`, `…-hwe-…`) count as kernel updates; kernel headers and tools (`linux-headers-*`, `linux-tools-*`, `kernel-tools`, `kernel-headers`) no longer do.
- Linux agent: each available update also reports its architecture and installed version (on dnf/yum also the package name without `.arch`; on pacman the repository), and the update list the distribution release from `/etc/os-release`. `patch_install` takes `{"name", "version"}` entries that install exactly that version. The server stores every reported update as a package version per distribution release, package, architecture, version and repository, with the time Octofleet first saw it on any node, and each node's pending updates as rows per version – the base for Linux approval rules with a minimum age. An unchanged update list costs one indexed read per push; at 10,000 nodes with 150 updates each, a changed list took 18 ms (median) ([#271](https://github.com/BenediktSchackenberg/octofleet/issues/271)).
- Troubleshooting guide: Windows update installations that fail with `0x800F0823` or are offered again after the restart, where API installations show up (not in *Settings → Update history*), diagnosing an installation on the node (update history, Setup events, DISM, CBS and Windows Update logs, servicing processes that must never be stopped), component store cleanup after many cumulative updates, and the Linux agent's logs.
- Linux agent: its log (`/var/log/octofleet-agent.log`) is rotated. `install.sh` and the service (at every start, so also after a self-update) add `/etc/logrotate.d/octofleet-agent`: weekly or at 10 MB, 8 compressed files kept, `copytruncate`. Settings `LOG_ROTATE_COUNT`, `LOG_ROTATE_MAXSIZE`, `LOGROTATE_FILE` (empty: off). A configuration whose marker line was deleted is left alone; without logrotate the agent warns. The service writes `/etc` through a transient systemd unit, since it runs with `ProtectSystem=strict`. Uninstalling removes the rotated logs and the managed configuration.
- **Fleet updates** (Patches → Fleet updates, `/patches/updates`): all nodes, Windows and Linux, with their pending and security updates, the reboot state (pending, will need / may need one), the last update search with its status and source, and a running search or installation; cards that count and filter (with pending updates, security updates, reboot, failed search, no search for 7 days, offline), name and OS filter, sorting by column, all kept in the URL with Back working. Each node leads to its Updates tab. Tick nodes to **search for updates** or **install updates** on all of them – on Windows only the updates approved in the catalog, Linux nodes not in bulk yet (no approval path): the confirmation lists each node with its approved updates and reboot outlook, offers the reboot choice when a reboot can be needed, and leaves Defender signature updates out unless asked; the rows show the running search or installation and a failed one with a link to the job. An installation counts as running until the node reports after its restart (or while it waits for one), so it is not started again by mistake; it can be overridden. API: `GET /api/v1/patches/fleet`, `POST /api/v1/patches/fleet/search`, `POST /api/v1/patches/fleet/install` (the server builds each node's payload). Linux reboot estimate: `libssl3t64` (Ubuntu 24.04 and later) counts as OpenSSL ([#271](https://github.com/BenediktSchackenberg/octofleet/issues/271)).
- Windows nodes: the Updates tab gets **Search for updates** and **Install updates** / **Install selected (n)** like Linux nodes, with checkboxes on the available updates; the confirmation asks what to do when an update needs a reboot (no reboot, reboot at a set time, in one minute). After an installation the Windows agent searches again and sends a fresh inventory. The tab counts the pending updates on Windows too (it counted the installed ones and the history); a scheduled reboot time is read with its offset (it was taken as local time and compared with UTC). Linux nodes get the same reboot choice (a systemd timer runs `systemctl reboot`). A Windows installation that runs longer than 30 minutes is reported as still running, with the servicing processes, and never stopped. The update tables share their column widths; successful results are shown quietly, failed ones in red. The Windows installation result lists each KB's result code and HRESULT and is checked against the Windows Update history: a KB reported as installed but recorded as failed there (e.g. `0x800F0823`, a newer servicing stack installed first; the update has to be installed again after the restart) now fails the job with a hint, instead of being reported as installed. The update history keeps the newest entry per update and result (an update installed twice was stored once, and the older failed attempt overwrote the success), and the installed updates show the newest attempt's result. The install confirmation says whether a reboot is needed (Windows reports it per update and whether one is pending; on Linux it is estimated from the package names) and offers the reboot choice only then.
- Linux nodes: **Search for updates** (`patch_scan`: refresh the package lists with apt, dnf or yum and report the updates, with the result as the node's last update search) and **Install updates** (`patch_install`: all updates, or the packages selected in the list). The inventory reports whether a reboot is required. The Updates tab of Windows nodes lists the available updates of the last search. The tab of Windows and Linux nodes turns amber while updates are pending (not counting Defender signature updates) and red when the last update search failed ([#230](https://github.com/BenediktSchackenberg/octofleet/issues/230)).
- Agents update from the Octofleet server: the server serves verified releases, and the Windows agent checks for a newer one every 6 hours or on a `restart-agent` job ([#158](https://github.com/BenediktSchackenberg/octofleet/pull/158), [#168](https://github.com/BenediktSchackenberg/octofleet/pull/168), [#173](https://github.com/BenediktSchackenberg/octofleet/pull/173)).

- Vulnerability scan: OSV advisories are cached between scans (`osv_advisories`) and downloaded again only when OSV reports a change or the entry is older than 30 days; a scan of 1,833 software versions downloaded 10,549 advisories every time. A failed Windows push is retried after about 5 minutes instead of every minute. Jobs and *Collect inventory* still push immediately (#283).

### Changed
- **Linux agent: one log per component** ([#330](https://github.com/BenediktSchackenberg/octofleet/issues/330), step 1 for the Linux agent): `/var/log/octofleet-agent/` holds `Agent.log`, `Inventory.log`, `Jobs.log`, `Updates.log`, `Remediation.log`, `Security.log`, `LiveData.log`, `RemoteTools.log` and `SelfUpdate.log` – the Windows agent's component names – and `Agent.log` also gets every warning and error of the other components. Lines read `2026-11-15T16:26:04.561+01:00 INFO [Updates] job=… patch_install: Installed updates: 1 of 1 (nginx)`: ISO 8601 with milliseconds and offset (before: local time without zone), level, component. Jobs log their name and type at the start and result, exit code, duration and the last output line on failure at the end; update searches, installations and reboots log what they refreshed, installed, held back and scheduled in `Updates.log`. Levels `debug`, `info` (default), `warn`, `error` in `config.env`: `LOG_LEVEL` for all, `LOG_LEVEL_<COMPONENT>` (e.g. `LOG_LEVEL_UPDATES=debug`) for one. Every line still goes to the journal, with its component. A line is written with bash built-ins – no `date` and `tee` process per line any more (about 0.05 ms instead of 2 ms). logrotate now covers `/var/log/octofleet-agent/*.log` – each file weekly or at 2 MB, 4 kept (before: 10 MB, 8 for the single file); the managed configuration is updated at the next start – and the agent runs logrotate itself after writing 2 MB, as logrotate runs only daily. At the first start the old `/var/log/octofleet-agent.log` and its rotated copies move into the folder (as `octofleet-agent.log.0`, `.1`, …) and the old path becomes a link to `Agent.log`. `install.sh`, `uninstall.sh` and the `uninstall-agent` job know the folder; `LOG_FILE` only names the old file now.
- **Event counters from hourly counts:** the counters on Security → Events, the dashboard's 7-day widget and the security dashboard counted every stored event on each refresh (0.3–1.3 s with 8 million events, growing with the fleet). They now read hourly counts from two TimescaleDB continuous aggregates (`event_counts_hourly`, `file_event_counts_hourly`; size by event types and hours, not by nodes), refreshed by the database every 30 minutes; newer events are counted at query time, so the numbers stay current. Measured with 2 million events: 82–114 ms → 5–8 ms, same counts. The aggregates are created at the first start and filled right away by the database in the background (seconds to minutes); until then the counters are as slow as before.
- **Fleet → Nodes is the Fleet workspace** ([#298](https://github.com/BenediktSchackenberg/octofleet/issues/298)): the node tree moved there from the dashboard. On the left: *All nodes*, *Groups* → group → OS → release (e.g. *Linux* → *Ubuntu 24.04 LTS*) and *Not in a group* the same way, each with its node count (tooltip: how many are online). Picking a branch shows its nodes in the list on the right; the branch is in the URL (`?group=&os=&release=`), so Back, reload and links keep it, and the list's title, counts and sorting follow it. The tree stays on the left of each node page and keeps its open branches for the browser session, so opening a node no longer loses the user's place; the terminal, shell, screen and live pages stay full-width. Each group links to its settings (the gear on hover), *Groups* to the group list. Below tablet width the tree is hidden and the list shows the picked branch as a chip that clears it. The tree lists counts, not every node, and loads from `GET /api/v1/nodes/tree?view=summary` (counts per group, OS family and release, with the node IDs per release; one query: the groups in one grouped pass, the feature version only looked up for Windows nodes; at 10,000 nodes in 50 groups 69 ms and 128 KB, where the full tree takes 356 ms and 2.1 MB). - **Tasks page:** a failed job no longer stays a task after it was fixed – failures are one entry per node and job type (and job name for commands, scripts and packages), and an entry drops out once a later run of the same kind succeeded on that node (*Show resolved job failures* shows them, dimmed, with the time of the success). - **Retention is applied** (Admin → Retention, moved from Security: it also covers performance data and hardware changes; `/security/retention` forwards there): security events, file audit events, performance data and hardware changes are kept for a set time – by default 30, 90, 30 and 365 days – and older data is compressed after 7 days (not hardware changes). The settings were stored but nothing applied them, so the database grew without limit (security events: about 1.3 GB per week from a single Windows node). The page gets *Keep (days)*, *Compress after (days)* and *Legal hold* per data type, a Save button (it saved on every keystroke) and shows the stored size, the oldest data and the jobs. The never-applied hot/warm/cold days and the categories findings, evidence exports and UI audit events are no longer shown. Changing a setting needs `settings:write`. Compression measured on one day of security events: 180 MB → 11 MB. New chunks of the events, file events and performance tables cover one day instead of seven, so retention keeps close to the set time.
- The 7-day event rollup is removed: it aggregated events into hourly counts and then deleted them row by row (on a large table that is slow and bloats the table), and `POST /api/v1/events/rollup` with it. - Agents ask for terminal commands much less often while no terminal is open ([#283](https://github.com/BenediktSchackenberg/octofleet/issues/283)): about every 5 s instead of every 0.5 s (Windows) or every second (Linux). The nginx example in docs/CONFIGURATION.md no longer leads to `/api/api/v1` and forwards the WebSockets of shell, screen sharing and terminal.
- **Auto-Fix: one remediation job per node and update** instead of one per CVE ([#197](https://github.com/BenediktSchackenberg/octofleet/issues/197)): 7-Zip 15.14 with 21 CVEs gives one job that lists the 21 CVEs it closes (`cve_ids`, shown in the job list), not 21 jobs running the same `winget upgrade`. A scan that runs again while the job waits creates no second job; CVEs found since then are added to the waiting job (`cves_added`). Approval stays required by default. The agent poll also sends `cveIds`; agents need no update.
- **Auto-Fix: fix packages with a winget package ID** ([#197](https://github.com/BenediktSchackenberg/octofleet/issues/197)): without a fix command, winget updates exactly that package (`winget upgrade --id <ID> --exact`) instead of searching by the display name; packages without an ID work as before. 32-bit installations (registered under `WOW6432Node`, as the Windows agent's inventory reports) are updated with `--architecture x86`. The one-click fix shows the command the agent really runs.
- **Backend: routes registered twice** ([#298](https://github.com/BenediktSchackenberg/octofleet/issues/298), first step): 19 old copies in `main.py` of routes that a router already registers are gone (nodes detail, history and register, jobs list/detail/create, metrics summary and timeseries, deployments create/list/detail, legacy alerts and alert stats, provisioning tasks and images, `GET /api/v1/pxe/{mac}`). FastAPI always ran the router's route, so no request is answered differently. The test that every write route needs credentials now also checks the routes of the included routers (before, it only saw the routes defined in `main.py`).

Every full batch also dropped one event; fixed.
- Windows agent: the log no longer fills with connection errors. The screen and live-data pollers asked the server every 5 seconds, just when the server closed the idle connection after 5 seconds (`SocketException 10053`, about 100 errors with stack traces a day). The agent now closes idle connections after 2 seconds, and all its HTTP calls share one connection pool (the security collectors opened a new connection for every upload). A server that is not reachable, a dropped connection or a timeout is logged as one warning line per part of the agent, then at most every 5 minutes with the count, and once when it works again; the pollers back off meanwhile (the terminal poller asked every 0.5 seconds while the server was down). "Service not configured" at every start is an information about the optional gateway connection when the Octofleet server is set up.
- Linux agent: a failed inventory push is retried after a minute (`PUSH_RETRY_INTERVAL`, doubling with every further failure up to the push interval, with random jitter), not after the full push interval. After a reboot, the first push often fails because the server is not reachable yet (on the Octofleet server itself, its containers are still starting); the node then showed the state from before the reboot, e.g. "Reboot required", for up to 30 minutes.
- The date format picked in the language menu shows as labeled in every language: with the UI in English or Spanish, "31.12.2026" gave 31/12/2026.

The sidebar badges say what they count (tooltip): the Jobs badge counts failed jobs of the last 7 days (it counted all failed jobs ever), the Alerts badge alerts that could not be sent (it counted the alert rules). The jobs page reads `?status=failed`.

### Upgrade
- Job instances get their kind of run at startup in the background, newest first, for the last 90 days (about 80 s for 2.5 million instances); until then the Tasks page may list a failed job that a later run already fixed.
- **Retention upgrade protection:** existing installations keep their database policies unchanged until an admin reviews and explicitly activates each data type under Admin → Retention. Activation replaces existing policies and may permanently delete older data. Fresh installations use the defaults immediately. The old hot/warm/cold values were never applied and are not carried over.
- Scripts that read `/api/v1/admin/agent-live` or `/api/v1/remediation/live` need a valid session token (`?token=` or `Authorization: Bearer`) of a user with `settings:read` or `jobs:read`; the shared agent key no longer opens them. The web console already sends the token.
- Scripts that read jobs, exports, reports or other admin data with the shared agent key (e.g. `scripts/eventlog-scheduler.sh`, `scripts/metrics-scheduler.sh`) get 403 now: give them a personal API key of a user with the permission.
- Pending registrations of older Windows agents (no registration secret) can no longer fetch their configuration: update the agent – it registers again by itself – and reject the old entry among the pending nodes, or configure the machine with the install command.
- Custom roles stored with their own permission list need the read permissions of the pages their users see (e.g. `alerts:read`, `jobs:read`).
- **Network connection events stop at the update:** the server drops `network.connect` / `network.close` unless they are turned on (Security → Profiles → *Fleet default*, or a profile). Turn them on right after the update if you use them. Older Windows agents keep sending them until they update (the server drops them); new agents stop collecting them.
- Inventory push interval: installations keep the interval in their configuration – older installers wrote 30 minutes (`ScheduledPushIntervalMinutes` / `PUSH_INTERVAL=1800`), and reinstalling keeps it. Remove the setting (or set 60 / 3600) to use the new default; the spreading applies either way with the new agent versions.
- The agent poll routes `GET /api/v1/jobs/pending/{node_id}` and `GET /api/v1/remediation/jobs/pending/{node_id}` need the agent key (`jobs:poll`), like the result routes.
- `NEXT_PUBLIC_API_URL` in `.env` was ignored by the web console at runtime; set `BROWSER_API_URL` instead if the browser must use a different backend address (without `/api`). Behind a reverse proxy, leave it empty and forward `/api/` including WebSockets to the backend (docs/CONFIGURATION.md, *Reverse Proxy*).
- Remediation ([#197](https://github.com/BenediktSchackenberg/octofleet/issues/197)): the backend adds `remediation_packages.winget_id`, `remediation_jobs.cve_ids` / `vulnerability_ids` / `architecture` and `software_current.architecture` at startup; existing jobs get their one CVE as `cve_ids`. Existing pending and approved jobs keep running as they are. 32-bit programs are known after each node's next inventory push.

### Upgrade
- Scripts or monitoring that call `/api/v1/jobs/pending/…` or `/api/v1/remediation/jobs/pending/…` need the agent key (`X-API-Key`) now; without it they get 401. The Windows and Linux agents already send it.
- The central agent key (`API_KEY`) has the agent's permissions only (inventory, job polls and results). It counted as a full administrator, although every managed machine stores it. Windows agent: `C:\ProgramData\Octofleet` (with `service-config.json`, which holds the key) is restricted to SYSTEM and Administrators by the installer, at every service start and every hour; ProgramData let every local user read it and create files in it. The logs move to `C:\Windows\Logs\Octofleet` (readable without elevation), so nobody needs to open the folder. The key itself is stored DPAPI-encrypted for SYSTEM (`InventoryApiKeyProtected`), so widened folder rules do not expose it.

### Upgrade
- Scripts that called administrative routes with `API_KEY` (e.g. the terminal, node deletion, the password policy) get 403 now; use a user login or an API key from **API Keys** instead. Agents are not affected. The Windows folder rules, the key encryption and the new log folder come with the new Windows agent release; on its first start the service encrypts an existing plain-text key and moves the logs from `C:\ProgramData\Octofleet\logs` to `C:\Windows\Logs\Octofleet`. A plain-text `InventoryApiKey` written later (e.g. by a support script) is encrypted the same way.
- The backend applies its database changes (new tables, columns and the job type constraint) at startup; no manual SQL is needed.
- Patch catalog: at startup the backend adds the `not_required` state to the node entries (`patch_catalog_nodes` status check, replaced once; existing entries stay as they are) and an index on `(patch_id, status)`. Entries that earlier searches deleted are not recreated from scans; a Windows node's next inventory with its update history adds `installed` entries for catalog updates it installed after Octofleet first saw them.
- The backend creates the vulnerability cache and its triggers at startup and calculates every node once in the background; until it is done the pages show the nodes still being recalculated. `GET /api/v1/vulnerabilities/by-node` now returns at most 100 nodes unless `limit` (up to 1000) and `offset` are given.
- The agent-side changes need the new agent versions. Agents with server-based updates install a newer release published on the server within 6 hours, or right away on a `restart-agent` job.
- Slower idle terminal polling: older agents ignore the server's new `active` field and keep polling every 0.5–1 s. New agents with an older server still work: they poll fast for 60 s after a command came, so only the first command of a session waits up to 5 s.
